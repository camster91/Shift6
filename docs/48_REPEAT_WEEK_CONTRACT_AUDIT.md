## What already exists

- `app/review.tsx:595` exposes a confirmed **new six-week cycle**, explicitly saying it does not repeat a completed week. The integrated handover repository preserves its source history and records a new private destination. Do not relabel that operation as repeat-week.
- `src/domain/localPersistence.ts` and `src/db/cycleLifecycleRepository.ts` support owned, append-only, predecessor-checked pause/resume/review-date events. Resume preserves existing progress; it is not a return-dose prescription.
- `src/domain/scheduleRevision.ts:200` refuses moves of completed/future weeks and states they require a distinct attempt. It also refuses moving already-started occurrences. The existing baseline/date/timezone and revision receipts must remain intact.
- `app/workout.tsx:2175` gives individual session tries different IDs. Partial completion is a terminal receipt; a later session does not reopen it. This supports retrying an unfinished occurrence, but does not identify a new week run.
- No `repeatWeek` function or completed-week repetition writer was found by source search. `src/domain/shiftCalendar.ts` mentions repeat revisions in a forward-looking comment, not executable support.

## Concrete blockers

1. `src/domain/calendar.ts:106,125,242` groups status and occurrence identity by week/workout only. Any old completed session makes the same occurrence complete (`getOccurrenceStatus` gives complete precedence). A second week run therefore disappears into the first.
2. `src/db/cycleRepository.ts:213` counts DISTINCT completed workout IDs across the entire cycle/week. `completeWorkoutSessionAndAdvanceCycle` in `src/db/workoutRepository.ts:722` uses that count. Merely resetting currentWeek would instantly reuse the old completions and could advance twice.
3. `getInProgressWorkoutSession` in `src/db/workoutRepository.ts:228` queries cycle/week/workout only. `app/workout.tsx:131,438` accepts workoutId and binds it to currentWeek. Neither a reminder nor an old route can specify a week run safely.
4. `src/db/calendarRepository.ts:93` drops session identity and returns no week-run binding. Its override IDs and SQL uniqueness are also cycle/week/workout. Existing schedule revision history cannot represent a second calendar without overwriting the original.
5. Home reads week completion through `src/db/progressRepository.ts` and schedule/session projection; Home/Coach share `src/domain/trainingSelection.ts`, which requires an active cycle and currentWeek. A repeat of a terminal cycle cannot work truthfully by silently changing its completed status.
6. `src/domain/notificationSchedule.ts:90` filters currentWeek and emits a workoutId-only route. Reminder identities omit week-run identity. Old reminders could open the wrong run.
7. `src/domain/types.ts` has no week-run identity in TrainingCycle, WorkoutSession or schedule occurrences. `src/domain/localRestore.ts:724` validates cycle/version/week but has no attempt graph. Export, restore, deletion, review witnesses and progress display must be updated together; adding UI alone is insufficient.

## Smallest coherent model

Introduce a **week run** separate from both `cycleWeek` (the prescription week, 1–6) and a session attempt (one actual workout try). Preserve all existing cycles, six week statuses, sessions, actuals, timestamps, goals and original date baselines.

Use an immutable owned `week_repeat_receipt` containing operation ID, new weekRunId, source cycle/version/week, predecessor run, frozen source context, selected private prescription snapshot, explicit date/timezone, confirmation time and complete workout occurrence/date list. Keep run outcomes in an append-only run event chain, and bind each new session through a unique session→weekRun link. These can be implemented as small dedicated local tables; exact migration/export versions must be assigned after the current migrations, not hard-coded in this draft.

Existing sessions without a repeat binding belong to the original run, identified deterministically by cycle/week. That is identity normalization only: do not invent an original confirmation time, new dates or repeat events. Every newly started repeated session must have its owned binding inserted in the same transaction as the session. Never classify historical sessions by timestamp heuristics.

Derive one active training cursor from the confirmed open week run, otherwise the existing active cycle/currentWeek. This is the shared Home/Coach/workout/reminder selector. A completed cycle remains completed historically while its explicitly selected repeat run is active. Reject another open run or conflicting active cycle; direct the person to existing explicit pause/finish controls rather than implicitly switching them. An unfinished workout in the current context must be resolved before confirmation. Pause/resume of a repeated run needs explicit run events; do not reuse a cycle pause event that falsely reopens a terminal cycle.

The active repeated run counts only its bound sessions, and each required workout at most once. A partial session plus a later complete session in that run counts once; an old run's complete session counts zero. Finishing the repeat closes that run and returns to the frozen prior cursor, without changing the original cycle's completed weeks or advancing it again. Repeating a historical week and starting a new six-week block remain different actions. Abandoning a repeat retains its partial/terminal records and its explicit outcome.

Keep original calendar occurrences visible as history. New occurrences use `(cycleId, weekRunId, workoutId)` and their own confirmed anchor and append-only date revisions. Do not move or reuse the original schedule baseline. Preserve workout-day slots against the explicit repeat start date, and show all resulting dates in the confirmation, including timezone and conflicts. Date changes are calendar changes only.

Preview the exact private prescription to be used. Do not say this recreates an old performed dose when that historical prescription is unavailable. Do not automatically reduce/increase load, invent return thresholds, or run existing next-session progression as an undisclosed side effect of repeating. The confirmed snapshot determines initial targets; later progression/manual edits must use existing deterministic, owner-approved rules with visible provenance. Public catalogue approval remains required; the local repeat operation provides no qualification or content approval.

## Transaction and privacy requirements

Cancel makes no writes. Confirm uses a single exclusive transaction: look up an exact operation retry first; validate current owner, database/focus binding, cycle/version, completed source week, source session/history cutoff, lifecycle and schedule predecessors, training cursor, explicit date/timezone and snapshot; insert receipt/run root/cursor binding; read back. Changed payload under the same operation ID refuses. Later history append must not invalidate the original frozen historical receipt during restore, but altered/omitted prefix data must reject. No new goal, baseline measurement, provider packet, sync intent or permission is created merely by repeating a week.

The entry screen must distinguish **Resume this unfinished workout**, **Resume this paused run**, **Repeat completed Week N**, and **Start a new six-week cycle**. Confirming a repeat does not claim medical readiness or a prescribed return dose. Offer existing manual controls and reviewed guidance only.

### Storage/write seam to implement before UI activation

A repeat writer needs a read-only preview and one exclusive confirm transaction. Require verified foreign keys and trusted owner/database/focus guards. Exact committed operation lookup comes first, but still verifies owner and stored receipt binding; identical retry reads the saved outcome, changed payload refuses. A new commit rechecks the owned cycle/version/completed source week, immutable private prescription, source session prefix, lifecycle/schedule predecessors, prior cursor and absence of unresolved session/open run conflicts. It then inserts the receipt, start event and cursor reservation together and reads back their exact bindings. Cancel remains zero writes. Initial targets come from the frozen explicit private snapshot; do not run prior-session progression or adjust dose as an undisclosed repeat side effect.

Session creation must insert its unique owned run link atomically, never retroactively classify old rows. Saved sets/drafts/provenance stay on their session IDs. Terminal run completion/abandonment needs a predecessor-checked exclusive transaction and exact operation retry, preserving original cycle rows. Pause/resume use run events; a paused run still reserves the cursor. Before returning to the frozen prior original cursor, recheck it is still owned, compatible and available. If later lifecycle/cursor changes conflict, show explicit manual selection guidance; do not resume another cycle or overwrite a newer cursor automatically.

The pure module is groundwork, not a ready persistent serializer. Repository/API ingress and restore still need strict DTO parsing, canonical-byte validation, cross-table ownership/version checks and prefix corroboration against the actual SQLite rows. Exports must include unique links for every repeated session and forbid a foreign/unknown run. The prefix fix treats earlier or equal-cutoff starts as historical even when completion is later; those clock ambiguities fail closed. Genuinely later started attempts remain allowed. This timestamp cutoff only validates the frozen history; it never assigns a session to original versus repeated identity. Do not silently weaken that rule to permit a backdated import. Any need for richer ordered source witnesses must be explicit and reviewed across persistence/restore together.
